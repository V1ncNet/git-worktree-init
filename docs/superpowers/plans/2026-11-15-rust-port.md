# Rust port Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the Python tool with one Rust binary `git-wt` that keeps every behavior and every existing plugin, and release it through GitHub Releases, a Homebrew formula in this repository and the Nix flake.

**Architecture:** A Rust crate with a library `git_wt` and a binary `git-wt` grows next to the Python code. The Python package stays the shipped implementation until Task 12 switches over in one commit. Plugins run in a Python bridge process that the binary starts only when `worktree-init.plugin` is set. The bridge talks JSON lines over file descriptors 3 and 4 and keeps the `ctx` helpers in Python.

**Tech Stack:** Rust 2024 (at least 1.89), `serde_json`, `libc`, Python 3.12 for the bridge, pytest, GitHub Actions, Nix flake, Homebrew.

**Spec:** `docs/superpowers/specs/2026-11-15-rust-port-design.md`

## Global Constraints

- Rust edition 2024, `rust-version = "1.89"`. The lock uses `std::fs::File::lock`.
- The only crates are `serde_json` and `libc`, as dependencies and as dev-dependencies. Tests build temporary directories with `std`.
- The bridge uses the Python standard library only. Nothing goes into `pyproject.toml` dependencies.
- All messages go to stderr. Only help output (`-h`) goes to stdout. `--version` goes to stdout.
- Help phrases are lowercase without a final period. Help and usage errors exit with 129. Every usage and help text matches today's Python output byte for byte.
- The tool's own Git calls and every plugin subprocess run without `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` and `GIT_PREFIX`. The forwarded `git worktree add` and `git worktree remove` keep the caller's environment.
- Records, the token file `worktree-init-record`, the lock `<git-common-dir>/worktree-init.lock` and everything under `harness.git` keep today's format.
- Every commit passes, inside `nix develop`: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test` and `uvx pytest`. Do not run `rustup default`. The machine's `rustup` has no default toolchain on purpose.
- The Python modules under `git_worktree_init/` and their tests are the reference for behavior. Each port task names the Python file and test file it mirrors. Where this plan and the Python code disagree, the plan wins only where it says so explicitly.
- `git-wt hook` and `git-wt harness-hook` never panic on input. Arguments come from `args_os` and the environment from `vars_os`, both converted lossily. In `hook`, any error before the last filter exits 0 silently, as `hook.sh` does with `|| exit 0`.
- `serde` is not a dependency, so JSON is built with `serde_json::json!` and read from `Value` by hand.
- Commit messages follow Chris Beams, in English, without needless articles, and end with `Co-Authored-By: <model that wrote the commit> <noreply@anthropic.com>`.

## Review Focus

1. **A plugin prints to stdout or runs a child that writes to stdout.** The protocol must survive, and the output must appear on the caller's stdout as today. Test in Task 6.
2. **A plugin is configured but Python is missing or older than 3.12.** The hook fails with today's message naming `worktree-init.python`, the worktree stays and the repair command is printed. A repository without a plugin needs no Python at all. Tests in Task 6 and Task 8.
3. **A worktree prepared by the Python version is removed after the upgrade.** The binary reads the old record and tears it down. Test in Task 3 and Task 10.
4. **Ctrl-C at the prompt or during `apply`.** Exit 130 with `worktree-init: aborted` and the repair command, worktree in place. Test in Task 8 through a pty.
5. **The hook registration from the README is copied literally.** Git appends the hook arguments itself, so `post-checkout` must arrive with exactly three. A missing binary must not fail the checkout. Tests in Task 8 and Task 11.

### Task 5: Python side of the bridge

**Files:**
- Create: `git_worktree_init/bridge.py`, `tests/test_bridge.py`
- Reference: `git_worktree_init/plugin.py` for validation and messages

**Interfaces:**
- Produces the protocol. Each line is one JSON object. Rust writes requests to fd 3 and the bridge writes replies to fd 4. A reply is `{"ok": <result>}` or `{"error": "<message>"}`.

| Request | Result |
| --- | --- |
| `{"op": "load", "path": "<abs>"}` | `{"options": [<option>...], "sanitize_env": [...], "next_steps": bool, "teardown": bool}` |
| `{"op": "slot_of", "worktree": "<abs>"}` | integer or `null` |
| `{"op": "choices", "option": "<name>", "ctx": <ctx>}` | list of strings |
| `{"op": "apply", "ctx": <ctx>}` | `null` |
| `{"op": "next_steps"}` | list of strings |
| `{"op": "teardown", "ctx": <ctx>}` | `null` |
| `{"op": "exit"}` | no reply, process exits 0 |

- `<option>` is `{"name", "kind", "default", "help", "choices": [..] | null, "dynamic": bool, "ask": bool}`.
- `<ctx>` is `{"main", "target", "common_dir", "mode", "env", "worktrees", "source", "slot", "options"}` with paths as strings and `source` and `slot` possibly `null`.
- `load` applies every check of `plugin.load` with the same messages. A default that `json.dumps` rejects fails with `<path>: option <name> has a default that is not JSON`.
- The bridge keeps one run `Context`. `choices` and `apply` set its fields from `ctx` (paths become `Path`, `worktrees` a tuple). `next_steps` calls the plugin with that same instance. `teardown` builds a fresh `Context` each time, like `engine.teardown_context`.
- A plugin exception becomes `{"error": str(error)}` and the loop continues. The message for `load` keeps the `<path>: ` prefix from `plugin.load`. `KeyboardInterrupt` ends the process with 130.
- `main(fd_in: int = 3, fd_out: int = 4) -> int` first calls `os.set_inheritable` with `False` on both fds, so plugin children never hold the pipes, then runs the loop until `exit` or EOF.
- Loading copies the mechanics of `plugin.load`, not only its checks: the module name from the SHA-1 of the path and the registration in `sys.modules` before `exec_module`, which a plugin with a `@dataclass` needs.

### Task 6: Rust side of the bridge

**Files:**
- Create: `src/bridge.rs`, `tests/bridge.rs`
- Modify: `Cargo.toml` (add `libc`)

**Interfaces:**
- Consumes: protocol of Task 5, `options::OptionSpec`, `gitenv::Env`, `config::Entries`.
- Produces:
  - `bridge::Ctx { main, target, common_dir: PathBuf, mode: String, env: Env, worktrees: Vec<PathBuf>, source: Option<PathBuf>, slot: Option<u32>, options: Values }`, serialized as `<ctx>`.
  - `bridge::Plugin { pub path: PathBuf, pub options: Vec<OptionSpec>, pub sanitize_env: Vec<String>, pub has_next_steps: bool, pub has_teardown: bool, .. }`.
  - `bridge::locate(main: &Path, entries: &Entries) -> Option<PathBuf>` resolves like `plugin.locate`, including `~`.
  - `bridge::python(env: &Env, entries_cwd: &Path) -> String` returns, in this order, `WT_PYTHON`, `git config --get --type=path worktree-init.python`, `option_env!("WT_DEFAULT_PYTHON")` and `"python3"`.
  - `Plugin::start(path: &Path, python: &str, env: &Env) -> Result<Plugin>` sends `load`. A missing file fails with `plugin not found: <path>` before Python starts.
  - `Plugin::slot_of(&mut self, worktree: &Path) -> Result<Option<u32>>`.
  - `Plugin::choices(&mut self, option: &str, ctx: &Ctx) -> Result<Vec<String>>`.
  - `Plugin::apply(&mut self, ctx: &Ctx) -> Result<()>`.
  - `Plugin::next_steps(&mut self) -> Result<Vec<String>>`.
  - `Plugin::teardown(&mut self, ctx: &Ctx) -> Result<()>`.
  - Errors from the bridge become `Error::Plugin(message)`. `Drop` sends `exit` and waits.

Startup:
- The sources of `git_worktree_init/{__init__,options,config,context,gitenv,bridge}.py` are embedded with `include_str!` and passed as one JSON object `{module: source}` in `argv[1]`. No file is written. `config.py` is embedded only because `options.py` still imports it. Task 12 removes that import.
- Create two pipes with `std::io::pipe()`, which sets `CLOEXEC`. In `pre_exec`, first move the child's two ends above 10 with `libc::fcntl(fd, F_DUPFD_CLOEXEC, 10)`, then `dup2` those copies to 3 and 4. Only 3 and 4 survive `exec`. The `dup2` copies are not `CLOEXEC`. After `spawn` the parent drops the child's ends, so a dead bridge gives EOF.
- Start with the sanitized `env`, the caller's working directory and stdin, stdout and stderr inherited: `<python> -c <BOOT> <sources-json>`. There is no `-I`, see the spec.
- `BOOT` drops the working directory from `sys.path`, checks the version and only then builds the package from the sources. An old Python prints today's message and exits 1:

```python
import sys
if sys.path and sys.path[0] == "":
    del sys.path[0]
if sys.version_info < (3, 12):
    sys.stderr.write(f"worktree-init: needs python >= 3.12, got {sys.version.split()[0]} at {sys.executable}; set git config worktree-init.python\n")
    sys.exit(1)
import json, types
```
